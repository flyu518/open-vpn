# 1.0.0 macOS 验收记录

测试平台：Apple Silicon Mac。本文记录 1.0.0 macOS 安装包的构建与验收范围。

## 源码与 Windows 交接

- 拉取的远端 `main`：`5d9e477c040208324ab91d2198478e96b053fb9c`。
- Windows 已测源码对应 `e573b99c98aed347a57af85687d023bd2bc20052`；该提交到拉取时的 `main` 只有文档变化。
- 本轮最终 Mac 候选：`35c7676934bada80961ee6af73634c35f6ed748c`。先提交修正，再从新的构建目录生成两种架构的最终包。

本轮实际构建和测试发现两项兼容问题，均已修正并重新验证：

1. 共享核心无条件定义 `ASIO_DISABLE_LOCAL_SOCKETS`，使 macOS command agent 的 `peercreds`、`unix_fd` 等符号缺失，真实核心编译失败。改为仅在 Windows 定义；Windows 的宏展开保持原样，Mac 保留 Unix socket 通信。
2. 更新确认框测试仅提供 Windows EXE 资产，Mac 正确拒绝选择该安装包，导致用例失败。测试响应改为同时包含 Windows、Mac ARM 和 Mac Intel 资产，没有改变生产更新逻辑。

Windows 与 macOS 分别在目标系统构建并验收；Windows 测试结果见 [Windows 验收记录](1.0.0-windows.md)。

## Apple Silicon 安装与真实连接

通过系统安装器实际安装上表 ARM 包，向导显示“安装成功”。从 `0.0.3` 升级到 `1.0.0`，实际打开 `/Applications/OpenVPN.app`。

- 系统安装登记、应用 Bundle 均为 `1.0.0`。
- 已安装 UI、daemon、helper 的 SHA-256 分别与解出的最终 PKG 载荷完全相同；三者均为 ARM。
- 两条原有配置及顺序保留。配置索引和三份托管 `.ovpn` 文件逐一与升级前备份比较，内容哈希均相同；不把 tar 自动生成的 AppleDouble 元数据当作配置文件。
- 直接点击连接，daemon 使用原有钥匙串凭据；本轮未读取、导出或重新输入 VPN 密码。

真实网络验收顺序及结果：

1. A 连接成功，新建 `utun4`；随后 B 成功，新建 `utun5`，两条同时在线，界面计时及收发流量持续更新。
2. B 接入后，A 的地址、路由和接口 DNS 规范化快照保持一致；兼容模式显示与 A 重叠并跳过部分路由。
3. 只断开 B，A 保持在线，上述快照不变，B 的专属接口清理。
4. 重连 B 成功，A 的快照仍不变。
5. 只断开 A，B 保持在线，B 的地址、路由和接口 DNS 快照不变。
6. 断开最后一条后，daemon 活动会话为 0；本次新增接口清理，DNS 和原有隧道路由恢复到连接前基线。
7. 按 A、B 顺序重新连接，恢复验收开始前的双连接状态。

这些结果验证握手、独立隧道及资源生命周期。未指定业务访问目标，不宣称所有内网业务服务均已端到端验收。
